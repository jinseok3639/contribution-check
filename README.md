# Contribution Check

> GitHub 레포의 커밋/브랜치/PR을 분석해서, 팀원별로 **"무엇을 만들고 무엇을 고쳤는지"** 를 서술형으로 정리해주는 도구.

## 왜 만드는가

기존 기여도 분석 도구(GitHub Insights, RepoSense, naver/pr-stats 등)는 대부분 커밋 수, 추가/삭제 라인 수 같은 정량 지표에 머무릅니다. 이런 지표는 두 가지 문제가 있습니다.

- **게이밍하기 쉽다.** 포맷팅, 보일러플레이트, 리네이밍만으로도 라인 수는 쉽게 부풀릴 수 있습니다.
- **가치를 반영하지 못한다.** 버그를 잡은 한 줄과 자동 생성된 코드 500줄은 라인 수로는 구분되지 않지만, 실제 가치는 전혀 다릅니다.

정작 궁금한 질문 — "이 사람이 실제로 어떤 기능을 만들었는가" — 에는 어떤 도구도 답하지 않습니다. 이 도구는 그 질문에 답하는 것을 목표로 합니다.

## 하는 일

1. 레포의 커밋 / 브랜치 / PR을 분석해서 **프로젝트의 컨셉과 기능 목록**을 파악한다.
2. 각 기능에 대해 **누가 무엇을 만들고 수정했는지**를 서술형으로 정리한다.
3. "A 30% / B 70%" 같은 정량 판정은 제공하지 않는다 — 퍼센트로 줄이는 순간 위에서 지적한 것과 같은 게이밍 문제와 오해가 다시 생기기 때문.

## 확정된 설계 방향

### 판정 방식: 서술형, 퍼센트 없음
기능 단위로 "누가 무엇을 만들고 수정했는지"를 문장으로 제공한다. 정량 점수화는 하지 않는다.

### 기능 정의: 하향식 + 상향식 병행
- **하향식**: README, 문서, 이슈에서 기능/컨셉을 추출.
- **상향식**: 코드 구조 자체에서 기능 경계를 추론. 코드 자체가 설계라는 전제.

두 방식을 병행해서 문서화가 부실한 레포에서도 기능 단위를 잡아낼 수 있게 한다.

### 기여 판단: LLM이 커밋 메시지 + diff를 읽고 판단
- 커밋 메시지와 diff 내용을 LLM에 넣어 "이 커밋이 어떤 기능에 기여했는가"를 판단시킨다.
- **문서 커밋도 기여로 인정.** 코드를 안 짜는 팀원(기획, 디자인 문서화 등)의 기여를 커버하기 위함.
- **단, "diff를 읽는다"가 커밋 전수를 뜻하진 않는다.** 실제 시험(atio, 114커밋)에서도 이미 반복적 수정은 샘플링했다. 무엇을 얼마나 읽을지는 아직 미확정 (아래 "diff 커버리지 전략" 참고).

### 진행 방침: 점진적 발전
처음부터 완벽하게 설계하지 않는다. 작게 시작해서 실제 레포에 돌려보며 발전시킨다.

## 아직 미확정 — 설계 시 참고할 고려사항

- **many-to-many 문제**: 기능 하나가 여러 커밋/파일에 걸치고, 커밋 하나가 여러 기능에 걸치는 경우가 흔함. 완전히 깔끔하게 나뉘지 않는다. 겹치면 양쪽 기능 모두에 걸치는 것으로 인정하는 방향을 검토 중. 기능을 대/중/소분류로 계층화해도 이 문제 자체가 없어지지는 않지만, 소분류 노드 단위로 n:m 매핑을 명시하기는 더 쉬워진다 (`note/02-feature-taxonomy.md`).
- **git author ≠ 실제 작업자**: Squash merge, 대표 1인이 대신 push, 페어 프로그래밍 등으로 실제 작업자와 git author가 다를 수 있음. 완전 자동 판정 대신 근거(커밋 SHA, diff)를 함께 보여줘서 팀원이 직접 확인하고 반박할 수 있게 하는 방식을 고려 중.
- **AI 사용 여부 판별은 스코프 제외**: Claude Code 등의 `Co-Authored-By: Claude` 트레일러는 기본으로 꺼놓는 경우가 흔해서 신뢰할 수 없음. AI 보조 여부는 판별하지 않고, git author 자체를 기여 귀속 기준으로 삼는다.
- **결과물 포맷이 실행마다 다르다**: 실제 시험 결과(`sample_result/atio-main_result.md`, `sample_result/CG-master_result.md`)를 비교하니 섹션 구성·순서가 다르고, 신원 병합 정보 위치도 제각각이었다. 고정 스키마 초안(대/중/소분류 기능 트리 + 중분류 단위 서술)을 검토했으나, 레포가 라이브러리처럼 계층형인지 게임/앱처럼 병렬형인지에 따라 다르게 적용해야 해서 아직 미확정 (`note/02-feature-taxonomy.md`).
- **기능 목록의 세분화 수준**: 위 두 결과물 모두 최상위 기능 목록이 실제 서술 단위보다 훨씬 성겼다 (예: atio "스냅샷 버전 관리" 1항목 안에 최소 6개 하위 기능). 대/중/소분류 트리로 해결 시도 중 (`note/02-feature-taxonomy.md`).
- **diff 커버리지 전략**: 커밋 메시지만으로 "diff 확인 불필요"를 판단하면 위험하다 — CG 시험에서 메시지("Error Fix", "Refactor" 등)와 실제 diff가 다른 사례가 4건 나왔다. 기능 커버리지 기반 선별 + 메시지 신뢰도 필터(제네릭 키워드, diff 크기 이상치) 조합을 검토 중 (`note/03-scaling-large-repos.md`).
- **대형 레포 확장성**: 커밋/diff를 다 읽는 지금 방식은 소규모 레포(atio 114커밋, CG 41커밋)에서도 이미 샘플링 중이라, 상용 규모 레포에서는 그대로 못 쓴다. 계층적 요약, 사전 필터링, 커밋 클러스터링, 증분 분석을 후보로 검토 중 (`note/03-scaling-large-repos.md`).
- **구현 형태**: 지금처럼 Claude Code 세션에서 직접 판단시킬지, 독립 코드 도구 + LLM API로 만들지, 사용자가 API 키를 넣게(BYOK) 할지, 로컬 모델을 쓸지 미정. 스킬 → 스킬+헬퍼 스크립트 → 코드 도구 순의 점진적 전환안을 검토 중 (`note/04-implementation-approach.md`).
