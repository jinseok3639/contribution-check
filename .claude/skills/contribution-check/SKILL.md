# Contribution Check

깃 레포 하나를 분석해서 "팀원별로 무엇을 만들고 고쳤는지"를 기능 단위 서술형으로 정리한다. `sample_repo/`(atio, CG) 두 레포를 실제로 두 번 시험 분석하면서 나온 문제(포맷 불일치, diff 미확인, 기능 세분화 부족)와 그 해결책을 반영한 절차다.

## 절대 바꾸지 않는 원칙

1. **서술형, 퍼센트 없음.** "A 30% / B 70%" 같은 정량 판정은 절대 내지 않는다. "이 중분류 아래 소분류 5개 중 3개를 A가 만들었다" 정도의 개수 열거는 괜찮다.
2. **문서 커밋도 기여다.** 코드를 안 짜는 팀원(기획, 문서화, 테스트 시나리오 설계 등)의 기여도 똑같이 기능 트리 위에서 서술한다.
3. **git author 병합은 신뢰도를 구분한다.** 이메일 완전 일치나 GitHub noreply 고유 ID 일치처럼 강한 신호는 자동으로 합치고, 이름 유사성이나 로컬 로그인 계정 이메일처럼 약한 신호만 있으면 반드시 근거를 보여주고 사용자에게 확인받는다. 확정 후에는 "인물별 커밋 수 합 = 전체 커밋 수"로 검산한다.
4. **AI 사용 여부는 판별하지 않는다.** `Co-Authored-By: Claude` 같은 트레일러는 신뢰할 수 없으므로 무시하고, git author 자체를 귀속 기준으로 삼는다.
5. **diff 전수 확인은 하지 않되, 무엇을 왜 스킵/샘플링했는지 반드시 수치로 남긴다.** "많이 읽었다"가 아니라 "N개 중 M개를 어떤 기준으로 읽었다"를 최종 결과물에 명시한다.

## 절차

### 0. 준비

- 분석 대상 레포 경로와 브랜치를 확인한다 (기본 브랜치를 모르면 `git branch -a`로 확인).
- `<repo>/.temp_contribution_check/progress.json`이 이미 있으면 이전 실행이 사용량 제한 등으로 중단된 것이다. 처음부터 다시 하지 말고 거기 적힌 지점부터 이어간다 (3~4단계 참고).

### 1. 정량 조사 스크립트 실행

이 스킬 폴더의 `scripts/survey_commits.py`를 실행한다:

```
python scripts/survey_commits.py <repo> --branch <branch> > <repo>/.temp_contribution_check/survey.json
```

이 스크립트는 커밋마다 다음을 **결정론적으로** 계산해서 JSON으로 낸다 — 이런 계산은 커밋을 하나씩 눈으로 보고 판단할 일이 아니라 스크립트가 훨씬 빠르고 정확하다:

- 변경 파일, 추가/삭제 줄 수, 병합 커밋 여부
- 사전 필터 대상 여부(`prefilter_skip`: lockfile/vendored/빌드 산출물류 패턴), whitespace-only 여부(`whitespace_only`: `--ignore-all-space` 기준 실질 변경 0)
- 메시지 위험 신호(`message_risk_reason`): `"no_change_claim"`(refactor/cleanup/정리/정상화 등 "동작 안 바뀜" 주장 — 다른 단어가 아무리 구체적이어도 무조건 위험), `"vague_filler"`(fix/error/수정/오류 등 필러 단어로만 이루어진 메시지), 또는 `null`
- 레포 내 "진짜 작업" 커밋(병합·사전필터·whitespace 제외) 기준 diff 크기의 robust z-score(`size_zscore`, median/MAD 기반 — 평균 하나가 초기 스캐폴딩처럼 극단값이어도 안 흔들림)
- `message_reliability_flag`: 위 위험 신호가 있거나 크기가 극단치(`|z| >= 3.5`)면 true
- author를 이메일 완전 일치 / GitHub noreply 고유 ID 일치 기준으로 묶은 `identity_groups`

**스크립트의 한계 (알고 써야 함)**: prefilter 패턴은 npm/cargo류 생태계의 일반적인 vendored 폴더명만 안다 — CG 샘플의 `freeglut`/`glaux`/`glext`처럼 프로젝트 고유 이름의 벤더 라이브러리는 못 잡고, 대신 크기 이상치(`size_zscore`)로 걸린다(실제로 그렇게 확인됨). whitespace-only 판정은 말 그대로 공백만 — 주석만 지운 커밋은 안 걸리므로 `no_change_claim` 메시지 체크가 그 역할을 대신한다. 메시지 위험 신호는 영어/한국어 필러 단어 목록 기반이라 다른 언어 위주 레포면 스크립트의 `NO_CHANGE_CLAIM_KEYWORDS`/`VAGUE_FILLER_WORDS`를 그 자리에서 늘려써야 한다.

### 2. 신원 병합

`survey.json`의 `identity_groups`를 본다.

- **강한 신호로 이미 묶인 그룹은 그대로 확정한다.**
- **그룹끼리 이름 집합이 겹치면** (예: 두 그룹 모두 "Bori"/"Haetae"를 포함) 강한 병합 후보다 — 이런 경우는 근거를 남기고 병합해도 된다.
- **이름도 이메일도 안 겹치는 그룹들**(예: 완전히 다른 이름 두 개, 완전히 다른 이메일 두 개)은 절대 혼자 판단하지 말고, `AskUserQuestion`으로 후보와 근거(각 그룹의 커밋 수, 시기, 겹치는 작업 영역)를 보여주고 사용자에게 확인받는다.
- 병합 후 "인물별 커밋 수 합 == 전체 커밋 수"를 검산한다. 팀 인원수를 안다면 인물 수가 그 수와 맞는지도 확인한다.
- 이 판단 과정(어떤 신호로 어떻게 합쳤는지)을 기록해둔다 — 나중에 "신원 병합 근거" 절에 그대로 쓴다.

### 3. 레포 구조 판단 + 기능 트리

- README/문서/이슈에서 컨셉과 기능을 뽑는다(하향식) + 코드 디렉터리/모듈 구조를 훑어서 기능 경계를 추론한다(상향식). 두 결과를 합쳐 기능 트리 초안을 만든다.
- 이 레포가 **계층형**(코어→확장→운영이 층으로 쌓이는 라이브러리/서비스류)인지 **병렬형**(장면/화면/기능이 나란히 배치된 게임/앱류)인지 판단한다.
  - 계층형 → **대분류(시스템) → 중분류(통합 컴포넌트) → 소분류(컴포넌트)** 3단계.
  - 병렬형 → 대분류를 억지로 만들지 않고 **중분류(=최상위 기능 단위) → 소분류** 2단계로 접는다.
- 병합 커밋이 있다면(스크립트의 `is_merge`) 이건 기능 트리 노드가 아니라 별도로 취급한다 (6단계의 "브랜치 통합 역할" 참고).
- 트리를 `<repo>/.temp_contribution_check/taxonomy.md`에 저장한다 — 여기서 중단돼도 다시 안 만들도록.

### 4. 커밋별 분류 + 커버리지 결정 (체크포인트/재개)

`survey.json`의 커밋을 순서대로 처리한다. `<repo>/.temp_contribution_check/commits.jsonl`에 이미 기록된 sha는 건너뛰고 이어서 진행한다 — 이 단계가 사용량 제한으로 가장 끊기기 쉬운 단계라서, 끊기면 이 스킬을 다시 실행했을 때 여기서부터 자동으로 이어진다.

각 커밋에 대해:

1. `is_merge`가 true면 diff를 읽지 않고 "병합 — 통합 역할"로 기록한다 (충돌 해결로 실제 코드가 바뀐 게 의심되면 드물게 `git show -m <sha>`로 직접 확인).
2. `prefilter_skip` 또는 `whitespace_only`가 true면 diff를 열지 않고 "스킵 — 사전 필터/공백"으로 기록한다.
3. 나머지는 커밋 메시지 + 변경 파일 경로만 보고 기능 트리의 소분류 노드에 매핑한다 (아직 diff 안 읽음).
4. 이 커밋의 diff를 실제로 열어볼지 결정한다 — 아래 중 하나라도 해당하면 연다:
   - 매핑된 소분류 노드에 커밋이 아직 적다 (그 노드의 첫 커밋이거나, 노드 전체 커밋이 3개 이하).
   - 여러 소분류에 걸치는 것으로 보여 애매하다 (many-to-many).
   - `message_reliability_flag`가 true.
   나머지는 메시지+파일 경로 분류만으로 확정하고 diff는 읽지 않는다.
5. diff를 연 경우 실제로 읽고 분류를 확정/수정한다. 메시지와 다르면 ("메시지는 X지만 실제로는 Y") 그대로 적어둔다 — 이게 이 도구의 핵심 가치다.
6. 결과(`sha`, 매핑된 노드, diff를 열었는지 + 연 이유, 한 줄 요약)를 `commits.jsonl`에 한 줄씩 append하고 `progress.json`의 "여기까지 처리함" 마커를 갱신한다.

### 5. 서술 작성

`commits.jsonl`이 다 채워지면 중분류 단위로 서술을 쓴다.

- **헤더는 중분류 단위로만 만든다.** 소분류마다 헤더를 새로 만들지 않는다 — 그 안에서 커밋 SHA를 인용하며 한 사람(또는 여러 사람)의 작업 흐름을 문단으로 서술한다.
- 문서 커밋도 똑같이 서술한다.
- many-to-many(한 커밋이 여러 소분류에 걸침, 반대도 흔함)는 숨기지 말고 "이 커밋은 A.1과 A.2 양쪽에 걸친다"처럼 그대로 드러낸다.

### 6. 최종 리포트 조립 (고정 스키마)

아래 순서와 헤더를 반드시 지킨다 — 레포마다 섹션 구성이 달라지면 안 된다:

```
# {repo} 기여도 분석

## 개요
## 기능 트리
## 중분류별 기여 서술
## 팀원별 종합 요약
## 브랜치 통합 역할        (병합 커밋이 있을 때만 포함)
## 신원 병합 근거
## 커버리지 / 분석의 한계
```

"커버리지 / 분석의 한계"에는 반드시 수치를 남긴다:

- 전체 커밋 수 N (병합 커밋 P개 포함)
- 사전 필터/공백으로 스킵: M1개
- 메시지+파일 경로만으로 분류(diff 안 읽음): M2개
- diff를 직접 읽음: M3개 — "기능 커버리지 부족/애매함" 때문에 연 것 K1개, "메시지 신뢰도 낮음" 때문에 연 것 K2개 (겹칠 수 있음)
- N = P + M1 + M2 + M3 확인
- 이 레포를 계층형/병렬형 중 어느 쪽으로 판단했는지와 그 이유 한 줄

### 7. 마무리

- 완성된 리포트를 `{repo-name}-{branch}_result.md`로 저장한다 (사용자가 다른 경로를 지정하면 그쪽으로).
- `.temp_contribution_check/`는 다 쓴 임시 상태이므로 삭제한다. 대상 레포 자체 git에 이 폴더가 커밋되면 안 된다 — 지우기 전에 대상 레포의 `.gitignore`에 없으면 추가하거나, 최소한 삭제를 잊지 않는다.

## 스코프 아님 (지금은 안 만든다)

- 퍼센트/점수 산출, AI 사용 여부 판별 — 확정 원칙에서 이미 배제.
- 대형 레포용 계층적 요약(map-reduce 서브에이전트), 커밋 클러스터링, 레포가 계속 자랄 때의 증분 재분석 — 지금 규모(수십~수백 커밋)에서는 안 써도 되고, 실제로 이 스킬로 감당 안 될 만큼 큰 레포를 만나면 그때 별도로 설계한다.
