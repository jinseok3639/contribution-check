# Contribution Check

깃 레포 하나를 분석해서 "팀원별로 무엇을 만들고 고쳤는지"를 기능 단위 서술형으로 정리한다. `sample_repo/`(atio, CG) 두 레포를 실제로 두 번 시험 분석하면서 나온 문제(포맷 불일치, diff 미확인, 기능 세분화 부족)와 그 해결책을 반영한 절차다.

이 스킬 폴더의 구성:

- `scripts/survey_commits.py` — 1단계에서 돌리는 정량 조사 스크립트 (표준 라이브러리만 사용).
- `scripts/render_report.py` — 6단계에서 `analysis.json`을 HTML 대시보드 + Markdown으로 렌더링한다.
- `references/analysis-example.json` — `analysis.json` 스키마의 최소 예시.
- `references/report-template.html` — 렌더러가 스타일/스크립트를 읽어가는 결과물 뼈대. 직접 편집할 일은 거의 없다.

## 절대 바꾸지 않는 원칙

1. **서술형, 퍼센트 없음.** "A 30% / B 70%" 같은 정량 판정은 절대 내지 않는다. "이 중분류 아래 소분류 5개 중 3개를 A가 만들었다" 정도의 개수 열거는 괜찮다.
2. **문서 커밋도 기여다.** 코드를 안 짜는 팀원(기획, 문서화, 테스트 시나리오 설계 등)의 기여도 똑같이 기능 트리 위에서 서술한다.
3. **git author 병합은 신뢰도를 구분한다.** 이메일 완전 일치나 GitHub noreply 고유 ID 일치처럼 강한 신호는 자동으로 합치고, 이름 유사성이나 로컬 로그인 계정 이메일처럼 약한 신호만 있으면 반드시 근거를 보여주고 사용자에게 확인받는다. 확정 후에는 "인물별 커밋 수 합 = 전체 커밋 수"로 검산한다.
4. **AI 사용 여부는 판별하지 않는다.** `Co-Authored-By: Claude` 같은 트레일러는 신뢰할 수 없으므로 무시하고, git author 자체를 귀속 기준으로 삼는다.
5. **diff 전수 확인은 하지 않되, 무엇을 왜 스킵/샘플링했는지 반드시 수치로 남긴다.** "많이 읽었다"가 아니라 "N개 중 M개를 어떤 기준으로 읽었다"를 최종 결과물에 명시한다.
6. **결과물에 군더더기 설명을 넣지 않는다.** 보면 아는 것을 글로 다시 쓰지 않는다 (6-3 참고). 결과물에 들어가는 문장은 전부 "읽지 않으면 모르는 내용"이어야 한다.

## 절차

### 0. 준비

- 분석 대상 레포 경로와 브랜치를 확인한다 (기본 브랜치를 모르면 `git branch -a`로 확인).
- `<repo>/.temp_contribution_check/progress.json`이 이미 있으면 이전 실행이 사용량 제한 등으로 중단된 것이다. 처음부터 다시 하지 말고 거기 적힌 지점부터 이어간다 (3~4단계 참고).

### 1. 정량 조사 스크립트 실행

이 스킬 폴더의 `scripts/survey_commits.py`를 실행한다:

```
python scripts/survey_commits.py <repo> --branch <branch> > <repo>/.temp_contribution_check/survey.json
```

이 스크립트는 커밋마다 다음을 **결정론적으로** 계산해서 JSON으로 낸다 — 이런 계산은 커밋을 하나씩 눈으로 보고 판단할 일이 아니라 스크립트가 훨씬 빠르고 정확하다:

- 변경 파일, 추가/삭제 줄 수, 병합 커밋 여부
- 사전 필터 대상 여부(`prefilter_skip`: lockfile/vendored/빌드 산출물류 패턴), whitespace-only 여부(`whitespace_only`: `--ignore-all-space` 기준 실질 변경 0)
- 메시지 위험 신호(`message_risk_reason`): `"no_change_claim"`(refactor/cleanup/정리/정상화 등 "동작 안 바뀜" 주장 — 다른 단어가 아무리 구체적이어도 무조건 위험), `"vague_filler"`(fix/error/수정/오류 등 필러 단어로만 이루어진 메시지), 또는 `null`
- 레포 내 "진짜 작업" 커밋(병합·사전필터·whitespace 제외) 기준 diff 크기의 robust z-score(`size_zscore`, median/MAD 기반 — 평균 하나가 초기 스캐폴딩처럼 극단값이어도 안 흔들림)
- `message_reliability_flag`: 위 위험 신호가 있거나 크기가 극단치(`|z| >= 3.5`)면 true
- author를 이메일 완전 일치 / GitHub noreply 고유 ID 일치 기준으로 묶은 `identity_groups`

**스크립트의 한계 (알고 써야 함)**: prefilter 패턴은 npm/cargo류 생태계의 일반적인 vendored 폴더명만 안다 — CG 샘플의 `freeglut`/`glaux`/`glext`처럼 프로젝트 고유 이름의 벤더 라이브러리는 못 잡고, 대신 크기 이상치(`size_zscore`)로 걸린다(실제로 그렇게 확인됨). whitespace-only 판정은 말 그대로 공백만 — 주석만 지운 커밋은 안 걸리므로 `no_change_claim` 메시지 체크가 그 역할을 대신한다. 메시지 위험 신호는 영어/한국어 필러 단어 목록 기반이라 다른 언어 위주 레포면 스크립트의 `NO_CHANGE_CLAIM_KEYWORDS`/`VAGUE_FILLER_WORDS`를 그 자리에서 늘려써야 한다.

### 2. 신원 병합

`survey.json`의 `identity_groups`를 본다.

- **강한 신호로 이미 묶인 그룹은 그대로 확정한다.**
- **그룹끼리 이름 집합이 겹치면** (예: 두 그룹 모두 "Bori"/"Haetae"를 포함) 강한 병합 후보다 — 이런 경우는 근거를 남기고 병합해도 된다.
- **이름도 이메일도 안 겹치는 그룹들**(예: 완전히 다른 이름 두 개, 완전히 다른 이메일 두 개)은 절대 혼자 판단하지 말고, `AskUserQuestion`으로 후보와 근거(각 그룹의 커밋 수, 시기, 겹치는 작업 영역)를 보여주고 사용자에게 확인받는다.
- 병합 후 "인물별 커밋 수 합 == 전체 커밋 수"를 검산한다. 팀 인원수를 안다면 인물 수가 그 수와 맞는지도 확인한다.
- 이 판단 과정(어떤 신호로 어떻게 합쳤는지)을 기록해둔다 — 나중에 "신원 병합 근거" 절에 그대로 쓴다.

### 3. 레포 구조 판단 + 기능 트리

- README/문서/이슈에서 컨셉과 기능을 뽑는다(하향식) + 코드 디렉터리/모듈 구조를 훑어서 기능 경계를 추론한다(상향식). 두 결과를 합쳐 기능 트리 초안을 만든다.
- 이 레포가 **계층형**(코어→확장→운영이 층으로 쌓이는 라이브러리/서비스류)인지 **병렬형**(장면/화면/기능이 나란히 배치된 게임/앱류)인지 판단한다.
  - 계층형 → **대분류(시스템) → 중분류(통합 컴포넌트) → 소분류(컴포넌트)** 3단계.
  - 병렬형 → 대분류를 억지로 만들지 않고 **중분류(=최상위 기능 단위) → 소분류** 2단계로 접는다.
- 병합 커밋이 있다면(스크립트의 `is_merge`) 이건 기능 트리 노드가 아니라 별도로 취급한다 (6단계의 "브랜치 통합 역할" 참고).
- **모든 중분류는 소분류를 최소 1개 가져야 한다.** 소분류가 최종 결과물의 행 단위이자 기여 귀속의 최소 단위라서, 여기서 덜 파면 표에 그 중분류가 통째로 빠진다 (atio 시험 분석에서 실제로 소분류 0개인 트리가 나왔다). 중분류를 적어놓고 그 아래를 못 채우겠으면 그건 중분류가 아니라 소분류였던 것이므로 한 단계 내린다.
- 트리를 `<repo>/.temp_contribution_check/taxonomy.md`에 저장한다 — 여기서 중단돼도 다시 안 만들도록.

### 4. 커밋별 분류 + 커버리지 결정 (체크포인트/재개)

`survey.json`의 커밋을 순서대로 처리한다. `<repo>/.temp_contribution_check/commits.jsonl`에 이미 기록된 sha는 건너뛰고 이어서 진행한다 — 이 단계가 사용량 제한으로 가장 끊기기 쉬운 단계라서, 끊기면 이 스킬을 다시 실행했을 때 여기서부터 자동으로 이어진다.

각 커밋에 대해:

1. `is_merge`가 true면 diff를 읽지 않고 "병합 — 통합 역할"로 기록한다 (충돌 해결로 실제 코드가 바뀐 게 의심되면 드물게 `git show -m <sha>`로 직접 확인).
2. `prefilter_skip` 또는 `whitespace_only`가 true면 diff를 열지 않고 "스킵 — 사전 필터/공백"으로 기록한다.
3. 나머지는 커밋 메시지 + 변경 파일 경로만 보고 기능 트리의 소분류 노드에 매핑한다 (아직 diff 안 읽음).
4. 이 커밋의 diff를 실제로 열어볼지 결정한다 — 아래 중 하나라도 해당하면 연다:
   - 매핑된 소분류 노드에 커밋이 아직 적다 (그 노드의 첫 커밋이거나, 노드 전체 커밋이 3개 이하).
   - 여러 소분류에 걸치는 것으로 보여 애매하다 (many-to-many).
   - `message_reliability_flag`가 true.
   나머지는 메시지+파일 경로 분류만으로 확정하고 diff는 읽지 않는다.
5. diff를 연 경우 실제로 읽고 분류를 확정/수정한다. 메시지와 다르면 ("메시지는 X지만 실제로는 Y") 그대로 적어둔다 — 이게 이 도구의 핵심 가치다.
6. 결과(`sha`, 매핑된 노드, diff를 열었는지 + 연 이유, 한 줄 요약)를 `commits.jsonl`에 한 줄씩 append하고 `progress.json`의 "여기까지 처리함" 마커를 갱신한다. `diff를 열었는지`는 6단계에서 각 기여의 `diff_read`가 되고, 열었는지/왜 열었는지의 집계가 `coverage`가 되므로 빠뜨리지 않는다.

### 5. 서술 작성

`commits.jsonl`이 다 채워지면 중분류 단위로 서술을 쓴다.

- **헤더는 중분류 단위로만 만든다.** 소분류마다 헤더를 새로 만들지 않는다 — 그 안에서 커밋 SHA를 인용하며 한 사람(또는 여러 사람)의 작업 흐름을 문단으로 서술한다.
- 문서 커밋도 똑같이 서술한다.
- many-to-many(한 커밋이 여러 소분류에 걸침, 반대도 흔함)는 숨기지 말고 "이 커밋은 A.1과 A.2 양쪽에 걸친다"처럼 그대로 드러낸다.

### 6. 최종 리포트 조립 (고정 스키마)

**HTML을 직접 쓰지 않는다.** 지금까지의 판단을 `analysis.json` 하나로 정리한 뒤 렌더러를 돌린다:

```
python scripts/render_report.py <출력경로>/analysis.json --out-dir <출력경로> --basename {repo}-{branch}_result
```

이렇게 하는 이유는 **셀 수 있는 것을 손으로 적으면 반드시 어긋나기 때문이다.** 실제 시험 실행에서 "중분류 17"이라고 적어둔 값이 실제 16이었고, 커버리지를 19/7로 적었지만 실제로는 20/6이었다. 그래서 `analysis.json`에는 **판단(기능 트리·귀속·서술·근거 SHA)만** 담고, 파생 수치는 전부 렌더러가 계산한다:

- 소분류/중분류/대분류 개수, 사람별 관여 기능 수, 역할(주도/참여/수정) 집계, 2인 이상이 손댄 소분류 수
- 통합표의 `rowspan` 값, 사람 색(`--p1`~`--p10`을 커밋 수 내림차순 배정), SVG 차트의 좌표·눈금·날짜 라벨·끝점 라벨 충돌 회피
- 커버리지 검산 문장

스키마는 `references/analysis-example.json`을 보고 쓴다. 렌더러는 검증에 실패하면 결과물을 만들지 않고 **exit 1**로 죽는다 — 조용히 틀린 리포트가 나오는 것보다 낫다. 막히는 조건:

- 소분류가 하나도 없는 중분류 / 기여자가 없는 소분류 / 근거 SHA가 없는 기여
- `people`에 없는 사람에게 귀속, 주도·참여·수정이 아닌 역할값
- `total ≠ merge + prefilter + message_only + diff_read`, 인물별 커밋 수 합 ≠ 전체 커밋 수
- `timeline` 마지막 누적값 ≠ `people.commits`
- 사람이 11명 이상 (이 형식의 상정 범위 밖 — 팀을 나눠 여러 번 돌릴지 사용자에게 묻는다)

`references/report-template.html`은 렌더러가 스타일·스크립트를 읽어가는 원본이다. 디자인을 바꿀 때만 건드리고, 리포트를 만들 때 복사하지 않는다.

아래 6-1~6-3은 렌더러가 실제로 뽑는 결과물의 형태다 — 무엇이 왜 그렇게 나오는지 알고 `analysis.json`을 채우기 위한 설명이고, 손으로 만들라는 뜻이 아니다.

#### 6-1. HTML 대시보드

라이브러리를 쓰지 않는 자기완결 단일 파일(인라인 `<style>`/`<script>`, 차트는 인라인 SVG). 탭 4개를 고정한다:

1. **대시보드** — 기본 화면. 아래 6-2 참고.
2. **기능 분류 × 기여** — 기능 트리와 귀속을 합친 통합표 (6-3).
3. **기능별 서술** — 중분류 단위 서술을 `<details>`로 접어둔다.
4. **분석 근거** — 브랜치 통합 역할 / 신원 병합 근거 / 커버리지.

사람 필터(팀원 카드 클릭 → 그 사람 기여만 강조)는 탭을 넘어서 유지된다.

#### 6-2. 대시보드 탭 구성

- **팀원 카드** — 사람마다 `커밋 수 / 관여 소분류 n·전체 / 주도 개수` + 한 줄 요약.
- **누적 커밋 추이** — 가로축은 **실제 날짜 간격**(등간격 아님), 세로축은 사람별 누적 커밋. 사람 수만큼 선을 그린다.
- **기능 커버리지** — 전체 소분류 중 이 사람이 관여한 개수를 가로 막대로. 퍼센트가 아니라 `21 / 28`처럼 개수로 쓴다.
- **역할 구성** — 주도/참여/수정을 사람별 스택 막대로. 관여 개수만으로는 "만든 것"과 "고친 것"이 구분되지 않아서 필요하다.
- **KPI 타일** — 소분류 총 개수 / 2인 이상이 손댄 소분류 수 / 메시지 ≠ 실제 diff 건수 / diff를 직접 읽은 커밋 수.

#### 6-3. 기능 분류 × 기여 통합표

기능 트리와 기여 표를 따로 두 번 그리지 않는다. 하나의 표에 rowspan으로 합친다:

- 행 = 소분류 하나. **모든 중분류는 소분류를 최소 1개 가져야 한다** — 소분류 없는 중분류가 있으면 3단계에서 트리를 덜 판 것이므로 되돌아가서 채운다.
- 왼쪽 열(들) = 대분류/중분류. 각 셀의 `rowspan`은 그 아래 소분류 개수. (병렬형이면 중분류 열 하나, 계층형이면 대분류+중분류 두 열.)
- 마지막 열 = **기여**. 그 기능에 관여한 사람마다 한 줄씩: 역할 배지(주도/참여/수정) · 이름 · 근거 커밋 SHA · 메시지≠diff 표시 · 귀속 근거(diff 확인 / 메시지 추정).
- **사람을 열로 만들지 않는다.** 사람이 열이면 인원수만큼 표가 넓어지는데 대부분의 소분류는 관여자가 1명이라 표가 거의 빈칸이 된다. 사람을 행 안의 줄로 넣으면 인원수와 무관하게 레이아웃이 유지된다. 이 형식은 **10명 정도까지**를 상정한다.

#### 6-4. Markdown

렌더러가 HTML과 같은 내용을 아래 스키마로 함께 낸다. 버전 관리·diff·붙여넣기용이다.

```
# {repo} 기여도 분석

## 개요
## 기능 트리
## 중분류별 기여 서술
## 팀원별 종합 요약
## 브랜치 통합 역할        (병합 커밋이 있을 때만 포함)
## 신원 병합 근거
## 커버리지 / 분석의 한계
```

수치는 `analysis.json`의 `coverage`에서 나온다. 4단계를 처리하면서 아래를 세어두었다가 채운다:

- `total` 전체 커밋 수 / `merge` 병합 커밋 수
- `prefilter` 사전 필터·공백으로 스킵한 수
- `message_only` 메시지 + 파일 경로만으로 분류한 수 (diff 안 읽음)
- `diff_read` diff를 직접 읽은 수 / `read_reason_coverage`·`read_reason_reliability` 그 이유별 내역 (겹칠 수 있어 합이 달라도 된다)

`total = merge + prefilter + message_only + diff_read`가 맞지 않으면 렌더러가 죽는다. 계층형/병렬형 판단 근거는 `notes`에 한 줄 넣는다.

#### 6-5. 군더더기 금지 (원칙 6의 구체 규칙)

레이아웃 차원의 군더더기는 렌더러가 이미 안 만든다. 여기서 지켜야 할 것은 **`analysis.json`에 직접 쓰는 문장**(`paras`, `callout`, `blurb`, `notes`, `identities.basis`)이다. 시험 제작에서 반복적으로 지적받은 것들:

- **섹션 도입부 설명 문단.** "기능 분류 체계와 기여를 한 표에 합쳤다. 왼쪽 열이 기능 트리고…" 같은 문장 — 표를 보면 아는 내용이다. 꼭 필요하면 제목 옆 작은 회색 글씨 한 줄로 압축한다 (`중분류 10 · 소분류 28`).
- **도구 자기소개 / 푸터 면책 문구.** "이 도구는 퍼센트를 내지 않으며…" 같은 것. 결과물은 분석 결과만 담는다.
- **차트 주석.** "점선 = 12-12, 41건 중 26건이 몰린 날" 같이 그래프를 보면 보이는 설명은 넣지 않는다. 보조선도 마찬가지.
- **자명한 UI 안내.** "펼쳐 볼 수 있습니다" 류.
- 반대로 **남겨야 하는 것**: 기호 범례(●주도/◐참여/≠ 같이 봐도 모르는 것), 커버리지 수치와 한계 서술, 신원 병합 근거, 특정 커밋에 대한 판단 메모. 이건 군더더기가 아니라 내용이다.

### 7. 마무리

- 파일명은 렌더러가 `{repo-name}-{branch}_result.html` / `.md`로 붙인다. 저장 **위치**(`--out-dir`)는: 사용자가 출력 경로/디렉터리를 지정했으면 그곳에, 지정하지 않았으면 이 스킬을 호출한 세션의 현재 작업 디렉터리에. (분석 대상 레포 내부에 저장하지 않는다 — 리포트는 분석 산출물이지 대상 레포의 일부가 아니다.)
- 같은 이름의 파일이 이미 있으면 덮어쓰기 전에 사용자에게 확인한다 — 이전 분석 결과를 날리게 된다.
- `analysis.json`도 결과물 옆에 남긴다. 나중에 서술 한 줄을 고치거나 디자인을 바꿔 다시 뽑을 때 레포를 처음부터 다시 읽지 않아도 된다.
- `.temp_contribution_check/`는 다 쓴 임시 상태이므로 삭제한다. 대상 레포 자체 git에 이 폴더가 커밋되면 안 된다 — 지우기 전에 대상 레포의 `.gitignore`에 없으면 추가하거나, 최소한 삭제를 잊지 않는다.
